# TDD Rule

> ⚠️ **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"를 만들지 않는다.

## 우선순위

- **프로젝트의 CLAUDE.md / AGENTS.md에 TDD 규칙이 있으면 그것이 우선한다.**
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙과 충돌하면 프로젝트 규칙을 따른다.

## 1. 적용 기준

### TDD 필수

- 비즈니스 로직
- API (핸들러, 요청/응답 처리)
- 유틸 / 순수 함수
- **버그 수정** (재현 테스트를 먼저 작성하고 실패를 확인한 뒤 수정)

### TDD 불필요

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업/스타일)
- SQL

## 2. RED-GREEN-REFACTOR 사이클

### RED — 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 묶지 않는다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 RED는 RED가 아니다.
- **실패 이유가 "기능 미구현"이어야 한다.** 오타, import 오류, 문법 오류로 인한 실패는 RED가 아니다. 테스트를 고치고 다시 실행한다.

### GREEN — 통과시키는 최소 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 아직 테스트가 요구하지 않는 기능·분기·옵션을 넣지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 실행해서 확인한다.

### REFACTOR — 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **모든 테스트가 green인 상태를 유지한다.** 변경할 때마다 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 다음 RED로 간다.

### 반복

- 다음 동작에 대한 **RED로 돌아간다.** 모든 동작이 끝날 때까지 반복한다.

## 3. 삭제 강제 규칙

- **테스트보다 프로덕션 코드를 먼저 작성했다면, 그 코드를 삭제하고 RED부터 다시 시작한다.**
- **"참고용"으로 남기는 것도 금지**한다. 주석 처리, 별도 파일 보관, 복사해 두기 모두 포함한다. 삭제는 삭제다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드는 테스트도 30초면 끝난다. 단순하다고 믿은 코드가 가장 자주 깨진다. 테스트 없는 단순함은 검증되지 않은 주장이다. |
| "나중에 추가하겠다" | 나중에 쓴 테스트는 구현에 맞춰 작성되어 **즉시 통과**한다. 실패를 본 적 없는 테스트는 아무것도 증명하지 못한다. |
| "시간이 없다" | 디버깅과 회귀 수정이 더 오래 걸린다. TDD는 시간을 앞당겨 쓰는 것이지 추가하는 것이 아니다. |
| "삭제하면 낭비" | 매몰 비용 오류다. 검증되지 않은 코드를 유지하는 것이 진짜 낭비다. 다시 쓰는 건 테스트가 있으면 빠르다. |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 버릴 코드라면 테스트 비용도 작다. 버리지 않을 거라면 TDD 대상이다. |
