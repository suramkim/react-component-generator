# Commit

변경사항을 읽고, 리뷰어가 한 커밋씩 이해할 수 있는 단위로 나눠 커밋한다. 사용자에게 승인을 묻지 않고 끝까지 진행하며, 판단이 애매한 변경은 묻는 대신 커밋에서 빼고 결과 보고에 남긴다.

## 1. 변경사항 분석

다음을 함께 실행해 전체 그림을 잡는다.

```bash
git status --short
git diff --stat
git diff
git diff --cached
git log --format='%s' -15
```

- 추적되지 않은 파일(`??`)도 반드시 포함한다. 새 파일은 `git diff`에 나오지 않으므로 직접 읽어서 내용을 확인한다.
- 이미 스테이징된 변경(`git diff --cached`)이 있으면, 사용자가 의도적으로 골라둔 것일 수 있으니 그 묶음을 하나의 커밋으로 존중하고 다른 변경과 섞지 않는다.
- 사용자가 인자로 범위를 줬으면(예: "UI 쪽만") 그 범위만 다룬다.
- `git log`로 이 저장소에서 실제로 쓰는 타입·스코프 표기를 확인하고 그에 맞춘다.

### 커밋하면 안 되는 것

다음이 보이면 커밋에서 빼고 결과 보고에서 알린다.

- 비밀 정보: `.env`, `*.pem`, API 키·토큰이 들어간 diff
- 빌드 산출물·로컬 파일: `dist/`, `node_modules/`, `.DS_Store`, 개인 에디터 설정
- 디버그용 임시 파일, 남겨둔 `console.log`·`debugger` (지적만 하고 지우지는 않는다)
- 이번 작업과 무관해 보이는 삭제(예: 의도를 알 수 없는 설정 파일 삭제)는 커밋하지 않고 남겨둔다

## 2. 논리적 단위로 분류

"이 커밋 하나만 되돌려도 나머지가 깨지지 않는가"를 기준으로 묶는다.

- 하나의 기능·수정에 필요한 코드, 테스트, 타입, 스타일은 한 커밋에 둔다.
- 의존성 추가(`package.json`, lock 파일)는 그 의존성을 쓰는 코드와 같은 커밋에 넣는다.
- 기능 변경과 무관한 정리(포맷, 이름 변경, 설정)는 분리한다.
- 한 파일에 서로 다른 단위의 변경이 섞여 있으면, 대화형 `git add -p`는 쓸 수 없으므로 아래 기준으로 정한다.
  - 더 큰 단위 쪽 커밋에 파일 전체를 넣는다 (기본)
  - 사용자가 미리 요청한 경우에만 `git apply --cached`로 해당 hunk만 스테이징한다
- 변경이 작고 한 가지 목적이면 억지로 쪼개지 않고 커밋 하나로 둔다.

## 3. 커밋 메시지 작성

형식:

```
<타입>[(스코프)]: <한국어 요약>

[필요할 때만 본문: 왜 바꿨는지, 주의할 점]
```

| 타입 | 쓰는 경우 |
|------|-----------|
| `feat` | 사용자가 체감하는 기능 추가·변경 |
| `fix` | 버그 수정 |
| `refactor` | 동작은 같고 구조만 바꿈 |
| `chore` | 설정, 의존성, 빌드, 스킬·도구 파일 |

저장소 로그에 `docs`, `test`가 이미 쓰이고 있으므로 문서만 바꾼 경우 `docs`, 테스트만 바꾼 경우 `test`도 쓴다.

요약 규칙:
- 한국어로, 무엇이 바뀌었는지 결과 중심으로 쓴다. 예: `feat: 컴포넌트 창에 처음부터 재생 버튼 추가`
- 50자 안팎, 마침표 없이, 명사형 종결(`~추가`, `~수정`, `~변경`)로 끝낸다.
- 스코프는 변경이 한 영역에 모일 때만 붙인다. 예: `chore(skills): ...`
- 파일 이름 나열이나 "여러 수정" 같은 모호한 요약은 쓰지 않는다.
- 본문은 요약만으로 이유가 드러나지 않을 때만 쓴다.

환경(시스템 지시, CLAUDE.md 등)에서 커밋 트레일러(예: `Co-Authored-By`)를 지정하면 메시지 끝에 빈 줄을 두고 붙인다.

## 4. 계획 공유 (승인 불필요)

커밋하기 전에 계획을 한 번 출력하되, 답을 기다리지 않고 바로 5단계로 넘어간다. 사용자가 중간에 끊을 수 있도록 무엇을 커밋하는지만 보이게 한다.

```
커밋 2개로 나눠 진행합니다.

1) feat: 클래식 Mac 스타일로 앱 UI 전면 개편
   - src/App.tsx, src/App.css, src/index.css, src/main.tsx
   - src/components/*.tsx, src/components/TitleBar.tsx (새 파일)
   - package.json, bun.lock (폰트 패키지 추가)

2) chore(skills): commit 스킬 추가
   - .claude/skills/commit/SKILL.md

제외: .env.example 삭제 (이번 작업과 무관해 보여 포함하지 않았습니다)
```

사용자가 "승인받고 해줘", "먼저 보여줘"처럼 확인을 명시적으로 요청한 경우에만 이 단계에서 멈추고 승인을 받는다.

## 5. 커밋 실행

계획 순서대로 커밋마다 다음을 반복한다.

```bash
git add -- <이 커밋에 속한 경로들>
git diff --cached --stat   # 의도한 파일만 올라갔는지 확인
git commit -F - <<'EOF'
<메시지>
EOF
```

- `git add -A`, `git add .`은 쓰지 않는다. 경로를 명시해 계획에 없는 파일이 섞이지 않게 한다.
- 삭제된 파일도 `git add -- <경로>`로 스테이징된다.
- pre-commit 훅이 실패하면 `--no-verify`로 우회하지 않는다. 원인을 고친 뒤 새로 커밋한다. 스스로 고칠 수 없으면 거기서 멈추고 실패 내용을 그대로 보고한다. 이미 만든 커밋을 `--amend`로 고치지 않는다.
- 푸시는 하지 않는다. 사용자가 따로 요청할 때만 한다.

## 6. 결과 보고

끝나면 `git log --oneline -<커밋 수>`와 `git status --short`로 확인하고 다음을 짧게 알린다.

- 만든 커밋들의 해시와 메시지
- 커밋하지 않고 남겨둔 변경과 그 이유
